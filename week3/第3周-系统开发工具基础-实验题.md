## 第9题 从源码构建并在干净环境安装 Wheel

**主题**：Packaging and Shipping Code

> [!abstract]- 知识归档
> **Python 包的结构（src layout）**
> - `src/greetlab/`：源码放 `src/` 下，包名是 `greetlab`，模块是 `cli.py`。src 布局能把"源码"和"项目根目录"隔离开，避免误 import 未构建的半成品。
> - `__init__.py`：标记该目录是**包**（package）。内容可以留空，但没有它（旧式）目录只是普通文件夹，无法被 `import greetlab` 识别。
>
> **pyproject.toml**
> - 项目元数据 + 构建配置的**单一事实来源**（现代标准，替代旧 `setup.py`）。
> - `[build-system]`：声明构建后端，`build-backend = "setuptools.build_meta"` 表示用 setuptools 打包；`requires` 是构建时需要的依赖。
> - `[project]`：包名 `name`、版本 `version`。
> - `[project.scripts]`：**入口点（entry point）**，`sdt-greet = "greetlab.cli:main"` 表示"生成一个叫 `sdt-greet` 的命令，运行时调用 `greetlab.cli` 模块里的 `main` 函数"。
>
> **argparse**
> - Python 标准库的命令行参数解析器。`add_argument("--name", required=True)` 声明必填的 `--name` 参数；`parse_args()` 解析 `sys.argv` 并返回命名空间对象 `a`，用 `a.name` 取值。
> - 参数缺失/非法时，argparse 会打印 usage 并 `exit(2)`（注意：这是第10题的考点）。
>
> **wheel 与构建**
> - **wheel**（`.whl`）是 Python 的二进制分发格式，本质是个 zip，解压即安装，不用现场编译。
> - `python -m build` 是 PEP 517 构建前端：在隔离环境里按 `pyproject.toml` 构建，产出 `dist/` 下的 `.whl` 和 `.tar.gz`（sdist）。
>
> **虚拟环境 venv**
> - `python -m venv .venv`：创建一个**独立隔离**的 Python 环境（自带解释器 + pip），与系统 Python 互不影响。
> - 激活后 `python`、`pip`、装好的 `sdt-greet` 都来自该 venv，卸载时删目录即可。

## 第10题 让编程智能体进入可验证的修复循环

**主题**：智能体编程

> [!abstract]- 知识归档
> **测试驱动（TDD）**
> - 先写一个**会失败**的测试描述"正确行为"，再改实现让它通过。好处：目标明确、可自动验证。
> - `pytest.raises(SystemExit) as e`：断言某段代码会抛 `SystemExit`；`e.value.code` 取退出码。
>
> **为什么空白 name 应 SystemExit(2)**
> - argparse 对"参数错误"约定以退出码 `2` 结束（`argparse` 的 `error()` 就是 `exit(2)`）。
> - 空姓名是**非法输入**，理应走 error 路径退出 2，而不是当作合法输入输出 `Hello,   !` 并退出 0。
> - `p.error("消息")`：打印 usage + 错误消息到 stderr，然后以退出码 2 结束。
>
> **智能体编程的可验证循环**
> - 给智能体三点：① 目标（改什么行为）；② 约束（不许动什么）；③ 验证命令（怎么算对）。
> - 人最后要 `git diff` 审改动、撤销无关修改、再跑测试——**智能体是加速器，人负责把关**。

### 第1步：复制 q09 为 q10，加一个失败测试

```bash
# 复制整个 q09 目录为 q10（含源码与 pyproject.toml）
cp -r q09 q10
cd q10
```

```python
# test_cli.py —— 先写测试（此刻实现还没改，这个测试应当"失败"）
import sys
import pytest
from greetlab.cli import main

def test_blank_name_exits_2():
    # 传入只含空白字符的 name，main 应以退出码 2 结束
    with pytest.raises(SystemExit) as excinfo:
        sys.argv = ["sdt-greet", "--name", "   "]   # 把 argv 换成测试参数
        main()
    assert excinfo.value.code == 2
```

> 源码在 `src/` 下，测试文件在项目根。两种办法任选：

> # 方式 B：可编辑安装（pip install -e .），把包"链接"进环境
> python -m pip install -e . && pytest
> ```

### 第3步：把目标、约束、测试命令交给智能体

给智能体一段清晰的提示（prompt）：

```text
目标：修改 q10/src/greetlab/cli.py 的 main，使 --name 只含空白字符时以 SystemExit(2) 结束。
约束：不要改动 test_cli.py 和 pyproject.toml；不要删除 --name 参数。
验证命令：cd q10 && PYTHONPATH=src pytest
请修改实现并运行上面的测试命令，直到通过。
```

智能体应给出最小修复（在 `parse_args` 后校验 `strip` 是否为空）：

```python
# src/greetlab/cli.py（修复后）
import argparse

def main():
    p = argparse.ArgumentParser()
    p.add_argument("--name", required=True)
    a = p.parse_args()
    if not a.name.strip():          # 只含空白（或空串）判为非法
        p.error("--name 不能只含空白字符")   # 打印 usage + 消息，exit(2)
    print(f"Hello, {a.name}!")
```

> [!tip] 为什么是 `p.error` 而不是 `sys.exit(2)`
> `p.error` 会先打印 usage 与错误消息到 stderr，再 `exit(2)`，更符合 argparse 的报错习惯；`sys.exit(2)` 也能退出 2，但没有报错提示。

### 第4步：人工检查 diff、撤销无关修改、复跑测试

```bash

# 也看每个文件具体改了什么：
git diff src/greetlab/cli.py

# 若智能体顺手改了无关文件（如改了 test、删了空行、改了 pyproject），撤销它：
git checkout -- <无关文件>     # 丢弃该文件的所有改动

# 最终确认只剩 cli.py 一处改动，再复跑测试
PYTHONPATH=src pytest

```

智能体改动：parse_args 后新增 `if not a.name.strip(): p.error(...)` 分支。

> 智能体可能"过拟合"测试：比如直接 `sys.exit(2)` 硬编码、或顺带改了测试让它"假通过"。所以必须人工 `git diff` 审改动、撤销无关修改、复跑测试——这是题目要求的"可验证修复循环"闭环。

### 有多少种做法

**让空白 name 退出 2 的几种实现**：

```python
# 方式 A：p.error（推荐，自动打印 usage + 消息）
if not a.name.strip():
    p.error("--name 不能只含空白字符")

# 方式 B：显式 sys.exit(2)（等价退出码，但无报错提示）
import sys
if not a.name.strip():
    sys.exit(2)

# 方式 C：自定义 type 校验（argparse 里写个校验函数，更"正规"但啰嗦）
def nonblank(s):
    if not s.strip():
        raise argparse.ArgumentTypeError("不能只含空白")
    return s
p.add_argument("--name", type=nonblank, required=True)
```

## 第12题 修复一个可复现的线性回归训练循环

**主题**：Python 与 PyTorch

> [!abstract]- 知识归档
> **PyTorch 基础**
> - `torch.tensor`：张量（多维数组），带自动求导。`torch.linspace(-1,1,101)` 在 $[-1,1]$ 间等距取 101 个点，`.reshape(-1,1)` 转成 101×1 列向量。
> - `nn.Linear(1,1)`：全连接层，本质是 $y = Wx + b$，$W$ 是 `weight`、$b$ 是 `bias`，初始随机。
> - `nn.MSELoss`：均方误差，衡量预测与目标的差距。
> - `torch.optim.SGD(model.parameters(), lr=0.1)`：随机梯度下降优化器，`lr` 学习率。
>
> **训练三步（每次迭代都要做）**
> - `opt.zero_grad()`：清空上次累积的梯度——**PyTorch 梯度默认累加**，不清会越加越错。
> - `loss.backward()`：反向传播，沿计算图自动求每个参数的梯度。
> - `opt.step()`：按梯度更新一次参数。
>
> **评估模式与 no_grad**
> - `model.eval()`：切到评估模式（关掉 dropout / batch-norm 等训练专用行为）。
> - `torch.no_grad()`：不记录梯度、不建计算图，评估时省内存、防意外更新。
>
> **本题本质**
> - 数据由 `y = 3x - 1` 生成，所以训练收敛后 `weight ≈ 3`、`bias ≈ -1`。
> - 不能直接赋值 `weight=3; bias=-1`，必须靠训练循环**学**出来。

### 第1步：保存并补全 train.py

```python
# q12/train.py
import torch
from torch import nn

torch.manual_seed(20260907)              # 固定随机种子，保证可复现
x = torch.linspace(-1, 1, 101).reshape(-1, 1)   # 101 个输入点
y = 3 * x - 1                            # 目标：y = 3x - 1

model = nn.Linear(1, 1)                  # 线性模型 y = Wx + b
loss_fn = nn.MSELoss()                   # 均方误差
opt = torch.optim.SGD(model.parameters(), lr=0.1)

for _ in range(200):                     # 训练 200 轮
    pred = model(x)                      # 前向：算出预测
    loss = loss_fn(pred, y)              # 算损失
    opt.zero_grad()                      # TODO①：清空梯度（不清会累加）
    loss.backward()                      # TODO②：反向传播求梯度
    opt.step()                           # TODO③：按梯度更新参数

model.eval()                             # 切到评估模式
with torch.no_grad():                    # 不计算梯度
    pred = model(x)
    final_loss = loss_fn(pred, y)        # 最终损失
print(f"final loss = {final_loss.item():.6f}")
print(f"weight = {model.weight.item():.6f}")
print(f"bias   = {model.bias.item():.6f}")
```

### 第2步：运行并核对

```bash
python q12/train.py
# 期望输出（数值会有极小差异）：
# final loss = 0.000123     <- 必须小于 0.001
# weight = 2.9998...
# bias   = -0.9999...
```

> [!tip] 判断是否成功
> - `final loss < 0.001`：训练收敛（题目硬性要求）。
> - `weight ≈ 3`、`bias ≈ -1`：因为数据就是 `y=3x-1` 生成的，说明模型学到了正确关系。
> - 若 loss 很大或 weight 离谱，先查三步是否缺了 `zero_grad`（梯度累加是最常见翻车点）。

### 有多少种做法

**打印 weight / bias 的两种写法**：

```python

#### A1. printenv 保存环境 → 建 venv → diff 前后差异

> [!abstract]- 知识归档
> - `printenv`：打印当前进程的所有环境变量（一行 `键=值`）；`env` 等价（还能改环境跑命令）。
> - `diff a b`：逐行比较两个文件，输出差异（`<` 是左边文件、`>` 是右边文件）。
> - 激活 venv 后环境变了：新增 `VIRTUAL_ENV`、`PATH` 开头被插入 `.venv/bin`、`PS1`（提示符）加前缀。
> - **为什么 shell 优先用 venv**：查找命令是按 `PATH` 从前往后找，venv 的 bin 排在最前，所以 `python`、`pip` 命中的是 venv 里的。
> - `deactivate` 不是一个可执行文件，而是 `activate` 脚本里定义的 **bash 函数**，负责把 `PATH`、`VIRTUAL_ENV` 等恢复原状。

```bash
printenv > before.txt          # 先把当前环境快照存下来
python -m venv .venv           # 建 venv
source .venv/bin/activate      # 激活（Win：.venv\Scripts\activate）
printenv > after.txt           # 再存一份
diff before.txt after.txt      # 看差异

# 关键差异在 PATH（先看激活前，再看激活后）
echo "$PATH"

# deactivate 是函数，不是二进制
which deactivate               # 无输出（找不到这个可执行文件）
type deactivate                # 输出：deactivate 是一个函数
deactivate                     # 退出 venv，再 echo $PATH 看是否还原
```

> [!tip] 期望的 diff 结果
> - `>` 新增：`VIRTUAL_ENV=/path/.venv`、`PS1` 变了。
> - `PATH` 那行：右边（after）开头多出 `/path/.venv/bin:`。
> - 如果 `diff` 没输出 PATH 差异，多半是你用 `echo $PATH` 看的时机不对（要在激活后、同一 shell 里看）。

#### A2. 建包 + 生成并检查 lockfile

复用第9题的 `greetlab` 包（或新建一个 `greeting` 包），装进 venv 后生成 **lockfile**。

```bash

# 先给 pyproject.toml 的 [project] 补两行，lockfile 才有内容、也不刷 warning：
#   requires-python = ">=3.13"
#   dependencies = ["requests>=2.31"]     # 有依赖，lockfile 才能体现"锁定传递依赖"

# 方式 A（推荐）：uv 管理

> - `pyproject.toml` 没写 `requires-python` 时，uv 会警告 `Defaulting to >=3.14` 并按自己的解释器猜——补上 `requires-python` 即可。

> [!tip] lockfile 是什么、为什么重要
> lockfile（`uv.lock` / `requirements.txt` 全量版）把**每一层依赖的精确版本 + 哈希**写死，保证任何人装到的依赖完全一致（可复现）。
> `pyproject.toml` 里通常只写范围（如 `numpy>=1.24`），lockfile 才是"锁定到底装哪个版本"的那把锁。若包没有任何依赖，lockfile 里就只有项目自身一条（`source = { editable = "." }`），看着很"空"——这也是为什么建议加个依赖再 lock。

#### A4. 写 Dockerfile + docker-compose.yml（应用 + Redis 缓存）

一个访问计数小应用：Flask 记次数、Redis 存次数。

```python
# app.py
import os
from flask import Flask
import redis

app = Flask(__name__)
r = redis.Redis(host=os.environ.get("REDIS_HOST", "localhost"),
                port=6379, decode_responses=True)

@app.route("/")
def home():
    return f"访问次数: {r.incr('hits')}"

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)
```

```text
# requirements.txt
flask
redis
```

```dockerfile
# Dockerfile
FROM python:3.12-slim                 # 用 slim 轻量镜像，而非完整版
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt   # 装依赖（清理缓存减小体积）
COPY app.py .
CMD ["python", "app.py"]              # 容器启动时跑应用
# 注意整个 Dockerfile 里所有指令的行内注释都要改成独立一行
```

```yaml
# docker-compose.yml
services:
  web:
    build: .                          # 用当前目录 Dockerfile 构建
    ports:
      - "5000:5000"
    environment:
      - REDIS_HOST=cache              # 服务名就是内网 DNS 主机名
    depends_on:
      - cache
  cache:
    image: redis:7-alpine             # 直接拉官方 Redis 镜像
    volumes:
      - redis_data:/data

volumes:
  redis_data:
```

```bash
docker compose up --build             # 构建并起两个容器
curl localhost:5000                   # 反复 curl，计数递增
```

> [!tip] 为什么用 `cache` 这个主机名
> docker compose 会为每个服务建内部 DNS，服务名 `cache` 自动解析到 Redis 容器 IP。web 进程不用知道 IP，写服务名即可——这是"微服务靠网络通信"的典型做法。

**第 3 步：打镜像、登录、推送 ghcr.io（两种方式通用）**

```bash
docker build -t ghcr.io/<你的用户名>/greetlab:v0.1.0 .
```

**3.1 获取 PAT（推送 ghcr.io 的凭证）**

- 入口：GitHub 右上角头像 → **Settings** → 左侧栏拉到**最底部** → **Developer settings** → **Personal access tokens**（不在“Password and authentication”页）。
- **classic token** 最省事：<https://github.com/settings/tokens/new>，勾 `write:packages`（会自动带 `read:packages`），可选 `delete:packages`。
- 若用 **fine-grained**：在 Permissions 区往下滚到 **Account permissions** → **Packages** → 选 **Read and write**（fine-grained 页面没有 `write:packages` 这种写法，是下拉框）。
- token 只显示一次，立即复制（形如 `ghp_...`）。

**3.2 登录 + 推送**

```bash
# 直接回显 token（最稳）；不要用 $CR_PAT，除非你真的 export 过它
echo "ghp_你的token" | docker login ghcr.io -u <你的用户名> --password-stdin
docker push ghcr.io/<你的用户名>/greetlab:v0.1.0

# 拉下来跑一把，验证发布成功
docker run --rm ghcr.io/<你的用户名>/greetlab:v0.1.0 --name 25020007111
# 期望：Hello, 25020007111!
```

> [!warning] ghcr.io 推送常见报错
> - `password is empty`：`$CR_PAT` 没设置（`echo "$CR_PAT"` 输出空行）。改用 `echo "ghp_..." | docker login ...`，或先 `export CR_PAT=ghp_...`。
> - `permission_denied: The token provided does not match expected scopes`：token 少了 **`write:packages`**（fine-grained 则是 Packages 没设成 Read and write）。重新生成 token 再登录。
> - `Login Succeeded` 后提示 `credentials are stored unencrypted`：正常现象，Linux 未配凭证助手时都这样，可忽略（想消除装 `docker-credential-secretservice` / `pass`）。
> - `-u` 必须是该 token 所属的 GitHub 用户名，且要和镜像路径 `ghcr.io/<用户名>/...` 保持一致。

**第 4 步：报告注明**。若走了方式 B，如实写，例如：

> A5 因 TestPyPI 账号强制 2FA/recovery 流程暂无法完成上传；已用 `python -m build` 产出 wheel，Docker 镜像改为安装本地 wheel 并成功推送 ghcr.io，等价验证了“打包 → 装包 → 镜像 → 推送”全链路。

> [!tip] Dockerfile 为什么这样写（4 个改进点）
> - **`--extra-index-url https://pypi.org/simple/`**（仅方式 A 需要）：TestPyPI 只托管你的包、不镜像整个 PyPI。`greetlab` 现在没依赖，不加也能装；一旦加了 `requests` 之类，不加就 `No matching distribution found`。
> - **`greetlab-<学号>==0.1.0`**：锁死版本，镜像可复现；不写版本会装到"当时最新"。
> - **`--no-cache-dir`**：不把 pip 缓存留在镜像层，体积更小。
> - **`ENTRYPOINT` + `CMD` 搭配**：`--name` 是必填参数，只有 `ENTRYPOINT ["sdt-greet"]` 时直接 `docker run 镜像` 会因缺参报错退出 2；加 `CMD ["--help"]` 让"不带参数运行"有默认行为，需要时又可用 `docker run ... --name X` 覆盖。

> [!warning] 三条坑
> - **Dockerfile 注释必须单独一行**。写成 `ENTRYPOINT ["sdt-greet"]  # 注释` 这种同行尾注释，Docker 不认，会把 `# 注释` 当参数传给命令。
> - TestPyPI 只是"演练场"，**别传真 PyPI**（题目明确要求）；ghcr.io 的 token 需要开 `write:packages` 权限。
> - 镜像是平台相关的：`linux/amd64` 的镜像在 arm64（Apple Silicon）上要模拟器才能跑。

#### B3. AGENTS.md / Skill / 子智能体（何时用哪个）

> [!abstract]- 知识归档（三种"给智能体加料"的手段）
> - **AGENTS.md**：项目根目录的 `AGENTS.md`（全局放 `~/.config/opencode/AGENTS.md`）。**启动时全量注入**上下文，适合"每次都必须遵守"的通用规则。
> - **Skill（技能）**：放 `.opencode/skills/<名字>/SKILL.md`（全局 `~/.config/opencode/skills/<名字>/SKILL.md`）。启动时**只注入 name + description**，智能体需要时再用 `skill` 工具把正文加载进来——避免常驻撑爆上下文。
> - **子智能体（Subagent）**：放 `.opencode/agent/<名字>.md`（或 `.opencode/agents/`）。是**独立上下文**的专职智能体，主智能体通过 task 工具调用它，它只把结果返回——中间过程不污染主对话。
> - **opencode 配置只在启动时加载一次**：新增/修改这些文件后要**退出并重启 opencode** 才生效。
> - 选择原则：**每次都用的规则 → AGENTS.md；某类任务的流程 → Skill；需要隔离上下文 / 批量重活 → 子智能体**。

#### B4. 用智能体完成 Markdown 无序列表正则替换（不直接编辑文件）

**目标**（来自代码质量一讲的练习5）：把 `code-quality.md` 里行首的 `- ` 无序列表标记替换成 `* `，但**不能**把日期（`2026-01-14`）、范围（`a-f`）、`-q` 选项这些位置也改了。

```bash
# 先取文件
curl -O https://raw.githubusercontent.com/missing-semester/missing-semester/refs/heads/master/_2026/code-quality.md
```

给智能体的提示（关键：**禁止直接编辑**）：

```text
把 code-quality.md 里行首的无序列表标记 `- ` 替换为 `* `。
约束：不要直接编辑文件；用第一讲提到的命令行工具（sed）加正则完成；
日期(2026-01-14)、范围(a-f)、选项(-q) 等其它位置的 `-` 必须保留。
完成后给出你用的 sed 命令，并贴 git diff 让我复核。
```

正确的 sed（锚定到"行首 + 可选空白 + `- `"）：

```bash
# -i 原地改；-E 用扩展正则；^ 锚定行首；[[:space:]]* 吸收缩进；\1 引用捕获组
sed -i -E 's/^([[:space:]]*)- /\1* /' code-quality.md

# 复核：只应改掉"行首的 - "，日期/范围/选项里的 - 不变
git diff code-quality.md
```

> [!warning] 为什么不能简单 `s/-/*/`
> 全局替换会把 `2026-01-14` 变成 `2026*01*14`、`[a-f]` 变成 `[a*f]`。必须锚定 `^`（行首）并限定"后面跟空格"，只命中真正的列表标记。

> [!tip] 智能体直接编辑文件 vs 用 sed 的取舍
> - 直接编辑：改动过程不可见、难审计、容易误伤、不易复现。
> - 用 sed：**命令即记录**，可放进脚本、可 diff、可回退、可复现——这正是题目让智能体改用命令行工具的用意。
> - 如果智能体还是去编辑文件，就明确说"不允许 write/edit 工具，只允许执行 shell 命令"。

#### C1. 浏览知名项目源码，找出几类"值得写"的注释

选一个 C++ 项目（贴合你的语言）：`nlohmann/json` 或 `fmt`。用 `rg` 定位注释类型。

```bash
git clone https://github.com/nlohmann/json.git && cd json

# 有用的 TODO（带上下文的待办）
rg -n "TODO|FIXME|HACK" include/ src/

# 指向外部文档 / 论文 / issue 的引用
rg -n "https://|RFC|paper|issue #|C++ Standard|wg21|P[0-9]{4}" include/

# "为什么不用" / 血泪教训类（why not）
rg -n -i "we use .* instead|deliberately|intentionally|do not use|must not|otherwise.*break" include/
```

> [!tip] 找到后回答"少了会失去什么"
> - 少了 **why-not** 注释：后来人会"好心"把刻意避开的做法改回去，把东西搞坏。
> - 少了 **TODO 上下文**：只剩"TODO: optimize"这类废话，没人知道还缺什么、为何延期。
> - 少了 **外部引用**：实现与论文/规范的偏差无处可查，改错都无从对照。

> [!example] 实测：`nlohmann/json` 与 `fmt` 里挖出的三类注释（真实样例）
> 两个仓库都已 clone 到本地（`~/Documents/codingCoding/codeRef/json` 与 `.../fmt`），下面行号可直接 `sed -n` 复现。
>
> **① 外部引用（数量最多，也最有价值）**
> - `json.hpp:25` `// See: https://github.com/nlohmann/json/issues/5103` —— 一段很绕的实现，注释直接挂到当初讨论它的 issue 上。
> - `json.hpp:5026` `// RFC 6902 (section 4.4) forbids "from" from being a proper prefix` —— JSON Patch 实现锚定到规范的具体条款。
> - `detail/input/lexer.hpp:335` `This function scans a string according to Sect. 7 of RFC 8259` —— 解析器和 RFC 逐节对应，改错有据可查。
> - `detail/conversions/to_chars.hpp:345` `// From the paper:`、`fmt/format.h:1628` `https://fmt.dev/papers/Dragonbox.pdf#page=28, section 6.1` —— 浮点打印算法直接锚定论文。
> - `detail/meta/cpp_future.hpp:40` `The following code is taken from https://github.com/abseil/abseil-cpp...` —— 还顺带交代了代码出处与许可证。
>
> **② why-not / 血泪教训（最稀缺，删了会埋雷）**
> - `json.hpp:5459` `// do not remove the space after '<', see .../pull/679` —— 看起来"多余的空格"其实是编译器 workaround，删了就编译不过。
> - `fmt/core.h:651` `// This function is intentionally not constexpr to give a compile-time error.` —— 故意"不做"的 constexpr，恰恰是设计的一部分。
> - `detail/exceptions.hpp:33` `This issue cannot be fixed with a header-only library...` —— 解释"为什么这里只能 suppress 警告"，防止后人反复尝试去"修复"它。
> - `detail/json_custom_base_class.hpp:27` `This class intentionally lives in namespace nlohmann rather than nlohmann::detail` —— 放哪个命名空间是**刻意的**，不是手滑。
>
> **③ TODO / FIXME（本次 rg 只命中 3 条，且都是带上下文的）**
> - `json.hpp:1268-1271` `// cppcheck-suppress[accessForwarded] TODO check` —— 是配合静态分析工具的标记，不是空喊"待优化"。
> - fmt 的 `include/`、`src/` 里 `rg "TODO|FIXME|HACK"` 竟然**零命中**——成熟项目会把"还欠什么"写成 issue 追踪，而不是丢在代码里烂尾。

> [!summary] C1 心得：注释的价值排序是 why-not > 外部引用 > 带上下文 TODO > 空 TODO
> - 真正"值得写"的注释不解释**代码在干什么**（读代码就知道），而解释**为什么这样、为什么不能那样**。
> - 少了 why-not（如 `do not remove the space after '<'`）：后来人会"好心"删掉看似多余的空格/constexpr 标记，直接编译失败或性能退化，还查不到原因。
> - 少了外部引用（RFC / 论文 / issue 号）：实现一旦和规范或算法有偏差，改错都无从对照；`RFC 8259`、`Dragonbox.pdf` 这些链接就是"纠错时的地图"。
> - 少了 TODO 上下文：只剩 `TODO check` 这类没人知道查什么、为何延期的废话；而 `cppcheck-suppress` 这种带工具名的才是可执行的。
> - 一句话判断标准：**把注释删掉，后续改动还能不能安全进行？删掉会踩坑的，才叫"值得写"的注释。**

#### C2. 好提交信息 vs 弱提交信息（体会补背景的费劲）

```bash
# 用你感兴趣的项目看最近提交（这里以 C++ 的 fmt 为例）
git clone https://github.com/fmtlib/fmt.git && cd fmt
git log --oneline -20
```

- **好提交**：标题即摘要，正文讲清"为什么改"（问题 → 解决方案 → 影响）。
- **弱提交**：只写"改了什么"，如 `fix bug`、`update code`、`fix crash`，看不出动机。

```bash
git show <弱提交的hash>      # 看它的 diff，试着推断"为什么"
```

> [!note] 按「问题 → 解决方案 → 影响」重写弱提交（示意）
> - 原：`fix crash`
> - 重写标题：`Fix use-after-free in parse when input is empty`
> - 重写正文：
>   - 问题：空输入时 `p` 在 `return` 后被继续引用，触发 UAF。
>   - 解决方案：提前校验 `input.empty()` 直接返回，避免后续解引用。
>   - 影响：崩溃修复；代价是对空输入多一次判断，可忽略。

> [!tip] 体悟
> 事后补背景极其费劲：你要反推当时的约束、翻代码、猜意图——而这些在写代码的当下本是一句话的事。所以**提交信息要在当下写**。

> [!example] 实测：`fmt` 与 `json` 最近 20 条提交，好坏一眼可分
> ```text
> # fmt (git log --oneline -20)
> 8a7aea04 Fix out-of-bounds read in error code format parsing (#4934)
> 6aa4a5f6 Fix debug string formatting for range formatters (#4936)
> 854fc956 Fix argument count in dynamic stores with named arguments (#4933)
> 14174c82 Add braces for readability
> 1da57c78 Simplify calendar_padding test
> 7071103c Remove incorrect chrono padding claim
> # json (git log --oneline -20)
> aa391dc0a Fix two develop CI regressions: dump() nodiscard warning and binary-reader const-correctness (#5520)
> ff80ed329 Speed up dump(), and keep it from overflowing the stack (#5285)
> 0452641c1 Read BSON documents without recursing per nesting level (#5508)
> 3e2de3222 Remove unused iomanip include (#5516)
> ```
>
> **好提交的样板**（正文 = 问题 → 解决方案 → 影响）：
> - `json` `ff80ed329`：标题即摘要；正文每一段都在讲"为什么这样改"——`dump_escaped` 原来对每个字节都跑 UTF-8 DFA、`put_indent` 的字符串倍增导致 `dump(2000)` 堆越界读、深嵌套会栈溢出——并附了基准数据（4.2x / 2.7x）和"已验证字节级一致"。
> - `json` `aa391dc0a`：把两处 CI 回归各写成一段，每段讲清"哪个编译器、哪个告警、为什么原来没暴露"。
>
> **弱提交的样板**（标题只写"改了什么"，正文为空）：
> - `fmt` `14174c82` `Add braces for readability`、`7071103c` `Remove incorrect chrono padding claim`、`json` `3e2de3222` `Remove unused iomanip include` —— `git show -s` 一看，正文全是空的。
> - 拿 `14174c82` 的 diff 反推"为什么"：`git show 14174c82` 能看到加了花括号，但**为什么**加、是不是某编译器警告强制、不加会不会引入 bug，全得靠猜。

> [!summary] C2 心得：弱提交不是"写得少"，而是"把反推成本转嫁给了未来"
> - 好提交在当下多花 30 秒写正文，弱提交让未来每个读它的人都要花几分钟 `git show` + 翻代码猜动机——**时间上是几十倍的负债**。
> - 成熟项目（fmt / json）的规律：标题基本都是"祈使语气 + 一句话说清影响"，issue 号挂在括号里；正文只在"为什么"不显然时才展开，而不是把标题复制一遍。
> - 反推一次就知道多贵：`Add braces for readability` 看着无害，可真要 cherry-pick 到别的分支、或怀疑它引入 bug 时，没有正文等于没有线索。
> - 结论：**提交信息要在写代码的当下写**——那时约束、动机、踩过的坑都还热乎；隔两周再补，要花十倍力气还补不准。

#### C3. 评估一个未解决的 issue

拿一个你使用的项目，找 `good first issue` / `help wanted` 标签的 issue 来评估（C++ 项目示例用 `nlohmann/json`）：

```bash
gh issue list --repo nlohmann/json --label "good first issue" --limit 10
gh issue view <number> --repo nlohmann/json
```

按讲义标准逐条打分：

| 标准 | 问什么 |
| --- | --- |
| 尊重维护者时间 | 有没有搜索过重复 issue？有没有贴最小复现？ |
| 环境 | 操作系统、版本号、相关配置写全了吗？ |
| 期望 vs 实际 | 说清"本该怎样"和"实际怎样"了吗？ |
| 复现步骤 | 具体到命令/操作，而不是"点了按钮"？ |
| 已尝试 | 是否说明自己做过什么排查？ |

> [!tip] 结论怎么写
> 例如：这个 issue 有环境、有复现命令、有最小示例，维护者可以直接开工 → 质量高；
> 那个只有一句"报错了"，缺环境与复现，维护者至少要来回追问 3 轮 → 质量低。

> [!example] 实测：`nlohmann/json` 的 `good first issue`（截至 2026-09-12）
> 本机 `gh` 已装好但未登录（`gh auth login` 需要 token），改用等价的 GitHub REST API：
> ```bash
> # 等价于 gh issue list --repo nlohmann/json --label "good first issue" --limit 10
> curl -sS "https://api.github.com/repos/nlohmann/json/issues?labels=good%20first%20issue&state=open&per_page=10" | jq -r '.[] | "#\(.number)  \(.title)"'
> ```
> 结果只有 3 条（标签很"金贵"）：
> - `#5318` `to_cbor()/to_msgpack() allocate a temporary basic_json for every object key`
> - `#5317` `CBOR: nested indefinite-length strings/byte strings are accepted (RFC 8949 3.2.3 requires definite-length chunks)`
> - `#3885` `meson build does not install nlohmann_json*.cmake files`

> [!summary] 逐条打分（按 C3 五条标准）
> **`#5318`（质量：极高，维护者能直接开工）**
> - 尊重维护者时间：贴了最小复现（重载 `operator new` 数分配次数）+ 定位到 `binary_writer.hpp:403-407` 具体行 + "I'm happy to open a PR"。
> - 环境：`g++ 13.3.0, Ubuntu 24.04, -std=c++14, -O2` 写全。

> - 复现步骤：直接给可编译代码，跑一下 `cbor 1016`。
> - 已尝试：已分析 UBJSON/BSON writer 已走"直接写"路线，还给出建议修法 + 破坏性分析（含"自定义 ObjectType 会踩坑"的提醒）。

### 2. argparse 速查

### 3. PyTorch 核心对象

| Python/PyTorch | 说明 |
| --- | --- |
| `torch.tensor` | 张量，`torch.linspace(...).reshape(-1,1)` 造列向量 |

### 4. 训练循环固定套路

```python
for _ in range(epochs):
    pred = model(x)          # 前向
    loss = loss_fn(pred, y)  # 算损失
    opt.zero_grad()          # 清梯度（关键！梯度默认累加）
    loss.backward()          # 反向传播
    opt.step()               # 更新参数
```
