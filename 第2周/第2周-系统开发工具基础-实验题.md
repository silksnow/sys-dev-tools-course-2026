## 第5题 控制一个可清理的后台任务
**主题**：命令行环境：进程、信号与任务控制

> [!abstract]- 知识归档
> **信号（Signal）**
> - 信号是操作系统发给进程的"异步通知"，用来让进程停止、中断或退出。/操作系统用来**通知进程发生了某个事件**的一种软件中断机制。可理解为系统发给进程的“紧急短信”。
> - 常见信号：`SIGTERM`(15, 礼貌请求退出，可被捕获)、`SIGINT`(2, Ctrl-C 中断，可被捕获)、`SIGTSTP`(20, Ctrl-Z 挂起)、`SIGKILL`(9, 强制杀死，**不可被捕获**)、`SIGSTOP`(19, 强制挂起，不可捕获)。
> - `kill -l` 列出全部信号；`kill -TERM <PID>` 或 `kill -15 <PID>` 发信号。
>
> **trap**
> - `trap '命令' 信号...`：进程收到列出的信号时不走默认行为，而是执行 `命令`。这是注册命令，会持续生效直到脚本死亡
> - 本题 `trap 'echo CLEAN_EXIT >> cleanup.log; exit 0' TERM INT` 意思是：收到 TERM（SIGTERM，admin或sys默认终止请求）或 INT（SIGINT，用户前台打断，立即终止，ctrl+c）时，把 `CLEAN_EXIT` 追加写进 `cleanup.log`，再以退出码 0 正常退出。
> - **为什么禁止 `kill -9`**：SIGKILL 不可被捕获，进程会被直接强杀，`trap` 里的清理代码根本不会执行，`cleanup.log` 不会出现 `CLEAN_EXIT`，任务也就谈不上"可清理"。
>
> **前台 / 后台与任务控制**
> - 前台任务：占用终端，终端要等它结束才能再输入。
> - `Ctrl-Z`：向当前前台任务发 `SIGTSTP`，把它**挂起**（暂停，不是结束）。
> - `bg`：把最近一个挂起的任务放到**后台继续运行**（等价 `bg %1`）。
> - 或用`./worker.sh &`，进程一出生就在后台
> - `fg`：把后台任务拉回前台。
> - `jobs`：列出当前 shell 的作业；`jobs -l` 多显示 PID；`jobs -p` **只打印 PID**（题目要求用它取 PID，不许手抄）。
> - `%n`：`%`作业表索引前缀，`n`是一个正整数占位符，待填写。作业号（如 `%1`），可当 PID 用，如 `kill -TERM %1`。
> - **1. 什么是“作业号”（`%n`）？**  
当你把脚本放到后台运行（比如执行 `./worker.sh &`）时，Shell 会输出类似 `[1] 12345` 的信息。其中：
**`[1]`** 就是**作业号**（在当前 Shell 会话中的编号，从 1 开始递增）。
**`12345`** 才是真正的**系统 PID**（全局唯一的进程 ID）。
> - **2. 为什么说“可当 PID 用”？**  
 在 Linux 中，`kill` 命令默认接收的是 PID。但 Bash 内置的 `kill` 命令做了增强——**它支持直接识别 `%n` 语法**。
 当你执行 `kill -TERM %1` 时，Shell 会自动将 `%1` **翻译**成该作业对应的**进程组 ID**（通常等同于该后台脚本的主进程 PID）。
所以，从“发送信号的目标”这一功能来看，用 `%1` 和用具体的 PID（如 `kill -TERM 12345`）效果是一样的，因此说“可当 PID 用”。
> - **3. 核心价值：比直接用 PID 更方便**  
作业号是当前 Shell 分配的**局部序号**，你不需要费力去查 `ps` 或记住那一长串数字。比如你只起了这一个后台任务，直接 `kill %1` 就能终止，非常顺手。
>
> **重定向**
> - `> stdout.log`：标准输出(文件描述符 1)覆写；`2> stderr.log`：标准错误(文件描述符 2)覆写。二者可合并写成 `> stdout.log 2> stderr.log`。
>
> **关键坑**
> - `jobs -p` 要在 `kill` **之前**取，否则任务结束、作业消失就取不到了。
> - Ctrl-Z 在 Git Bash(MinTTY) 里有效；在 PowerShell/cmd 里 Ctrl-Z 是"EOF"语义，不起挂起作用。

### 第1步：建目录、写脚本、加执行权限

```bash
mkdir q05 && cd q05

# heredoc 写多行脚本，'EOF' 加引号防止内容被当作变量解析，保证 LF 换行
cat > worker.sh <<'EOF'
#!/usr/bin/env bash
# 调用 `/usr/bin/env` 这个程序，然后 `env` 会在当前用户的 `$PATH`（环境变量路径）中**从上到下搜索**，找到第一个名为 `bash` 的可执行文件来运行脚本。这种找bash方法更具可移植性，但也把参数位占了，无法加上执行选项。
trap 'echo CLEAN_EXIT >> cleanup.log; exit 0' TERM INT
n=0
while true; do
  echo "$n"
  n=$((n+1))
  # shell里默认一切都是字符串，`n=$n+1`变成字符串"0+1"，`n=($n+1)`变成以字符串"0+1"开头的数组变量，bash中圆括号用来定义数组。只有`$((...))` 是 Shell 专门规定的算术扩展，内部是数学算式，也可写成`((n++))`或`((n+=1))`
  sleep 1
  # wait a second，防止高速循环刷爆资源，主动出让CPU资源
done
EOF

# chmod +x 赋予执行权限（chmod = change mode，+x 加 execute 位）
# shebang 第一行 #!/usr/bin/env bash 让系统用 bash 解释本脚本
chmod +x worker.sh
```

### 第2步：前台启动并分别重定向 stdout / stderr

```bash
# 前台启动，stdout 写 stdout.log，stderr 写 stderr.log
# 脚本每秒 echo 一个递增数字，所以 stdout.log 里会是 0,1,2,3...
# 脚本没有 stderr 输出，所以 stderr.log 会一直是空文件（这符合题目"分别写入"的要求）
./worker.sh > stdout.log 2> stderr.log
```

此时终端被占用，屏幕上没有数字（被重定向走了），光标停住。

### 第3步：Ctrl-Z 挂起 → bg 后台继续 → jobs 确认

```bash
# 按下 Ctrl-Z（SIGTSTP），会看到类似：
#   [1]+  Stopped   ./worker.sh > stdout.log 2> stderr.log

bg        # 让挂起的任务在后台继续运行，看到 "[1]+ ./worker.sh &"

jobs      # 确认状态，看到 "[1]+  Running   ./worker.sh ..."
```

### 第4步：用 jobs -p 取 PID，发 SIGTERM 并等待结束

```bash
# jobs -p 只输出 PID（作业号对应的进程组组长 PID），不能手工抄写
jobs -p     # 例如输出 12345

# 方式 A（推荐，一条命令）：命令替换 $(jobs -p) 取 PID 直接发信号
kill -TERM $(jobs -p)

# 方式 B（更稳妥，先存变量）：先取 PID 再发，避免 kill 前作业消失
pid=$(jobs -p)      # 先取 PID 存进变量
kill -TERM "$pid"   # 发 SIGTERM
```

### 第5步：确认任务退出（禁用kill -9） + cleanup.log 出现 CLEAN_EXIT

```bash
# kill信号投递到队列后就返回，但目标进程可能正卡在 `sleep 1` 里（处于内核态睡眠）。它不会立刻跳出来执行 `trap`，它要等到下一次被内核调度到 CPU 上运行时，内核才会发现“哎呀，你有个信号要处理”，然后强行切到用户态执行你的 `trap` 里面的 `echo` 和 `exit`。
# 等待任务真正退出：用 wait 等这个 PID，或简单 sleep 1 让它有时间跑 trap
sleep 1
jobs                # 应已为空（或显示 [1]+ Done），说明任务退出

cat cleanup.log     # 应出现 CLEAN_EXIT
# 期望输出：
# CLEAN_EXIT
```

> [!tip] 信号流转全过程
> `kill -TERM` 把 SIGTERM 发给 worker.sh → bash 捕获 TERM（因为 trap 声明了 TERM）→ 执行 `echo CLEAN_EXIT >> cleanup.log` → `exit 0` 正常退出 → `jobs` 显示 Done。
> 若用 `kill -9`：SIGKILL 不可捕获，直接强杀，`cleanup.log` 不会写入，任务不可清理——这正是禁止 `kill -9` 的原因。

### 有多少种做法

**取 PID 的三种写法**（都满足"不手抄 PID"）：

| 写法 | 命令 | 说明 |
| --- | --- | --- |
| `jobs -p` | `kill -TERM $(jobs -p)` | 题目指定，最直接 |
| 作业号 | `kill -TERM %1` | `%1` 是作业号，等价于 PID |
| 进程名查找 | `pgrep -f worker.sh` 再 kill | 通用，但不如 `jobs -p` 贴合题目 |

**等待任务结束的两种写法**：

```bash
# 写法 A：wait 等特定 PID（更精确）。让子进程的最后一步变成检查并叫醒
# 2>/dev/null扔掉报错，不关心进程意外去处。但等待的PID不存在时wait还是会返回127，可以用|| ture抹掉返回
wait "$pid" 2>/dev/null

# 写法 B：sleep 一下再看 jobs（简单够用）
sleep 1 && jobs
```

## 第7题 用调试器定位归并排序缺陷

**主题**：Debugging

> [!abstract]- 知识归档
> **调试器（Debugger）**
> - 调试器让你在程序运行中**暂停**，查看变量、单步执行。核心操作：**断点**（运行到某行暂停）、**单步**（一次执行一行）、**观察变量**。
> - 两种等价选择：命令行 `pdb`（Python 标准库）和 VS Code 图形化调试器（背后用 `debugpy`）。
>
> **pdb 常用命令**
> - `python -m pdb 脚本.py`：以调试模式启动。
> - `b` / `break`：设断点（`b 行号` 或 `b 函数名`）；`c` / `continue`：运行到下一个断点；`n` / `next`：单步（不进入函数）；`s` / `step`：单步（进入函数）；`p 变量`：打印变量；`l` / `list`：看源码；`q` / `quit`：退出。
> - 一条命令同时打印多个值：`p i, j, left[i], right[j]`（逗号分隔）。
>
> **VS Code 调试**
> - `F9` 切换断点、`F5` 启动调试、`F10` 单步跳过、`F11` 单步进入、左侧"变量/监视"面板观察 `i`、`j`、`left`、`right`。
>
> **归并排序**
> - 分治：把数组二分递归排好，再用 `merge` 合并两个有序段。`merge` 里 `i` 走 `left`、`j` 走 `right`，每次取较小者放入 `result`。
>
> **关键坑（本题的缺陷）**
> - `else` 分支写的是 `result.append(right[i])`，`i` 是 **left** 的下标，应该是 `right[j]`（`j` 才是 right 的下标）。这会导致 `right` 越界（`IndexError`）或取到错的值。

### 第1步：建文件，先跑一遍确认错误

```bash
mkdir q07 && cd q07
```

```python
# merge_sort.py
def merge(left, right):
    result = []
    i = j = 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            result.append(left[i]); i += 1
        else:
            result.append(right[i]); j += 1  # 此处存在缺陷：right[i] 应为 right[j]
    return result + left[i:] + right[j:]

def merge_sort(a):
    if len(a) <= 1: return a
    m = len(a) // 2
    return merge(merge_sort(a[:m]), merge_sort(a[m:]))

print(merge_sort([3, 1, 4, 1, 5, 9, 2, 6]))
```

```bash
python merge_sort.py
# 期望：抛 IndexError（right 越界），或输出顺序错误
# 例如合并 [1,3] 与 [2] 时，else 分支取 right[1]，但 right 只有 1 个元素 → IndexError
```

### 第2步：用 pdb 设断点观察 i、j、left[i]、right[j]

```bash
python -m pdb merge_sort.py
```

```text
(Pdb) b merge          # 在 merge 函数入口设断点
(Pdb) c                # 运行到第一个断点
(Pdb) l                # 看当前代码
(Pdb) p i, j           # 打印两个下标
(Pdb) p left[i], right[j]   # 打印比较的两个元素
(Pdb) n                # 单步，反复执行 p/n，观察进入 else 分支时 right[i] 越界/取错
(Pdb) q                # 退出
```

> [!tip] 观察重点
> 当 `left[i] > right[j]` 走 `else` 分支时，本应取 `right[j]`，代码却取 `right[i]`。
> 当 `i >= len(right)` 时（left 较长、right 较短），`right[i]` 直接越界崩溃——这就是异常根源。

### 第3步：最小修复（不得用 sorted 替换归并排序）

```python
# 只改一处：right[i] → right[j]
def merge(left, right):
    result = []
    i = j = 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            result.append(left[i]); i += 1
        else:
            result.append(right[j]); j += 1
    return result + left[i:] + right[j:]
```


## 第8题 先测量，再优化慢速词频程序

**主题**：Profiling

> [!abstract]- 知识归档
> **性能分析（Profiling）**
> - "先测量再优化"：先用工具找出真正慢的地方（瓶颈），再改，避免凭感觉乱优化。
> - `time`：测总耗时（bash 内建命令，或 `python -m timeit` 测代码片段）。
> - `cProfile`：Python 内置 profiler，统计每个函数的调用次数和耗时。
>
> **cProfile 输出列含义**（`python -m cProfile -s cumulative 脚本.py`）
> - `ncalls` 调用次数、`tottime` 该函数自身耗时（不含子调用）、`percall` 平均、`cumtime` 累计耗时（含子调用）、`filename:lineno(function)` 位置。
> - `-s cumulative`：按 `cumtime` 从大到小排序，最能定位瓶颈。
>
> **复杂度（本题关键）**
> - 原程序 `if word not in unique` 每次对**列表**做成员判断，列表查找是 O(n)，总复杂度 O(n²)，3 万词非常慢。
> - 用 **set（集合）** 做成员判断是 O(1)（哈希表），整体降到 O(n)。
>
> **统计指标**
> - 中位数：把多次测量值排序取中间（偶数个取中间两个平均），比平均更抗波动。
> - 加速比 = 优化前中位数 ÷ 优化后中位数。
>
> **可重复**
> - `random.seed(20260831)` 固定随机种子，保证每次生成完全相同的 `words.txt`，前后对比才公平。

#### B1. cProfile / line_profiler / memory_profiler 比较插入排序 vs 快排


> [!tip] 结论
> - **插入排序**瓶颈：内层 `while` 反复比较/后移，O(n²) 次比较移动；**快排**瓶颈：递归调用与 `partition`。

> - 再看**原地版快排**后对比差异。附加题：`perf stat` 看指令数、缓存命中/缺失。

#### B4. stress + htop + taskset 限制 CPU

```bash
sudo apt install stress htop

# 1) 起 3 个吃满 CPU 的 worker，htop 观察（约 3 个核跑到 ~100%）
stress -c 3 &
htop

# 2) 用 taskset 把整个进程绑到核 0、2，再看 htop
taskset --cpu-list 0,2 stress -c 3 &
htop
```

> [!tip] 知识点：为什么 taskset 之后不是 3 个核满载？
> `stress -c 3` 会开 **3 个 worker 线程**，每个跑一个 CPU 死循环。不加限制时，内核把这 3 个线程调度到不同的核，所以能占满 3 个核。
> `taskset --cpu-list 0,2` 设置的是**进程的 CPU 亲和性（affinity）**，把整个进程（连同它的 3 个线程）都限制在核 0 和核 2 上。于是 3 个线程只能挤在**这 2 个核**里跑：最多 2 个核满载，第 3 个线程在排队等——所以看不到 3 个核满载。
> `taskset -c 0,2 命令` 是 `--cpu-list 0,2` 的短写法；`man taskset` 查看。

**附加题：用 cgroups 限制 `stress -m` 的内存**

```bash
sudo apt install -y cgroup-tools

# cgroups v2 里新建一个内存控制组
sudo mkdir -p /sys/fs/cgroup/limit_mem
echo 128M | sudo tee /sys/fs/cgroup/limit_mem/memory.max   # 上限 128M

# 把 stress 进程丢进这个 cgroup（先拿它的 PID）
stress -m 4 --vm-bytes 64M &        # 4 个 worker 各想分 64M，共 256M
STRESS_PID=$!
echo $STRESS_PID | sudo tee /sys/fs/cgroup/limit_mem/cgroup.procs
# 结果：stress 拿不到 256M，被限制在 128M 内，htop/top 看内存不再暴涨
```

> [!tip] 知识点
> `cgroups`（control groups）是内核的资源限制机制，按进程组限 CPU / 内存 / IO。cgroups v2 里写 `memory.max` 就是设内存上限，超过会回收甚至 OOM。题目要求"限制 `stress -m` 的内存"，用 cgroups 即可实现。

#### B5.（进阶）Wireshark 抓 curl 报文

`curl ipinfo.io` 发起 HTTP 请求并获取自己 IP 的信息，然后用 Wireshark 抓取 `curl` 发出的请求和收到的回复报文。

> [!abstract]- 知识归档
> **Wireshark**
> - 网络抓包分析工具，把网卡上经过的每个数据包按协议层层拆解显示。抓包要选**网卡**，看到的是真实线上的字节流。
> - **显示过滤器**（Display Filter）只影响"显示"，不影响"抓取"：你抓的是全量流量，再用过滤器筛出关心的部分。填 `http` 就只显示 HTTP 报文。
> - 常用过滤：`http`（所有 HTTP）、`http.request`（只请求）、`http.response`（只响应）、`ip.addr == 1.2.3.4`（只看某 IP）、`tcp.port == 80`（只看 80 端口）。
>
> **HTTP 报文结构**
> - **请求**：请求行（`方法 路径 版本`，如 `GET / HTTP/1.1`）+ 头部（`Host`、`User-Agent`、`Accept` 等）+ 空行 + 可选 body。
> - **响应**：状态行（`版本 状态码 原因`，如 `HTTP/1.1 200 OK`）+ 头部（`Content-Type` 等）+ 空行 + body（这里是 JSON）。
>
> **为什么必须用 http（明文）而不是 https**
> - `curl` 默认走 `http://`（明文），报文内容可直接在 Wireshark 里看到。若用了 `https://`，内容被 **TLS 加密**，只能看到握手报文（`tls`），看不到明文 HTTP，所以本题要抓明文 HTTP。
> - 判断依据：`curl ipinfo.io` 等价于 `curl http://ipinfo.io`。

**请求报文（GET）**，展开 `Hypertext Transfer Protocol`，能看到：

### 有多少种做法

**过滤器的两种粒度**：

```text
http              # 只看 HTTP 报文（题目要求，最粗）
http.request      # 只看请求，不显示响应
http.response     # 只看响应，不显示请求
```

**抓包的两种方式**：

| 方式 | 命令 / 操作 | 适用 |
| --- | --- | --- |
| GUI 抓包（推荐） | 打开 Wireshark → 选网卡 → 抓包 → 过滤器填 `http` | 直观，适合给助教展示 |
| 命令行抓包 | `tshark -i eth0 -f 'tcp port 80' -Y http` | 无 GUI 环境（服务器/WSL） |

> [!tip] 知识点小结
> Wireshark 抓到的就是"真实网络字节流"：`curl` 先把 `GET / HTTP/1.1` 明文发出去，服务器回 `HTTP/1.1 200 OK` + JSON。整个过程对明文 HTTP 完全可见；换成 HTTPS 就被 TLS 加密，`http` 过滤器就筛不出内容了——这正是"明文 vs 加密"的直观演示。

### C. 命令行环境 · 任务控制（2 题）

#### C1. 用 pgrep / pkill 结束进程（不手输 PID）

```bash
sleep 10000
# 按 Ctrl-Z 挂起
bg                 # 后台继续
pgrep -af sleep    # 找 pid：-a 显示完整命令行，-f 匹配完整命令行
pkill -f 'sleep 10000'   # 按命令行匹配结束，无需手抄 pid
```

> [!tip] 知识点
> `pgrep`/`pkill` 按进程名/命令行找并杀进程，比 `ps aux | grep` 再手抄 PID 更省事。`-f` 匹配完整命令行（默认只匹配进程名），`-a` 额外打印完整命令行。

#### C2. 编写 pidwait 函数（等某个进程结束）

```bash
# wait 只能等当前 shell 的子进程，跨会话无效；改用 kill -0 轮询
pidwait() {
  while kill -0 "$1" 2>/dev/null; do
    sleep 1
  done
}

# 用法
sleep 60 &           # 后台任务
pidwait $!           # 等它结束（$! 是最近一个后台任务 pid）
ls                   # 结束后再执行
```

> [!tip] 知识点
> - `kill -0 <pid>` **不发信号**，只检测进程是否存在：存在返回 0，不存在返回非 0。
> - `wait` 只能等**子进程**，跨 bash 会话无效，所以用 `kill -0` + 循环实现 `pidwait`。
> - `sleep 1` 降低轮询频率，避免空转烧 CPU。

### D. 终端多路复用 tmux（1 题）

> 来源：<https://www.hamvocke.com/blog/a-quick-and-easy-guide-to-tmux/>（入门）+ <https://www.hamvocke.com/blog/a-guide-to-customizing-your-tmux-conf/>（自定义配置）

> [!abstract]- 知识归档
> **tmux 是什么**
> - *terminal multiplexer*（终端多路复用器），相当于"终端里的窗口管理器"：一个终端窗口里开多个 window 和 pane，每个 pane 是一个独立 shell。
> - 三大概念，由大到小：**session（会话）> window（窗口，像虚拟桌面）> pane（分屏，每个 pane 一个 shell）**。
> - **client-server 架构**：tmux server 在后台保活所有 session；你用的只是 client。所以断网/关终端，session 不丢。
>
> **前缀键（prefix）**
> - 所有 tmux 命令都是"前缀键 + 命令键"两步：先按前缀，松开，再按命令键。默认前缀是 `C-b`（= 同时按 `Ctrl` 和 `b`）。
> - 本文记 `C-b x` 表示：按 `Ctrl+b`，松开，再按 `x`。
>
> **核心价值**
> - **会话保活**：ssh 断线后 session 仍在服务器后台跑，`tmux attach` 接回来，现场原封不动。
> - **跨平台**：Mac / Linux / 服务器 / 树莓派通用，配置是一个 dotfile，可同步。

```bash
bind - split-window -v
unbind '"'
unbind %

# ---- 3) 一键重载配置：改完按 C-a r 生效，不必退出会话 ----
bind r source-file ~/.tmux.conf

# ---- 4) 不用前缀直接切 pane：Alt+方向键 ----
bind -n M-Left  select-pane -L
bind -n M-Right select-pane -R
bind -n M-Up    select-pane -U
bind -n M-Down  select-pane -D

# ---- 5) 鼠标模式：点窗口/点 pane/拖边界调整大小 ----
set -g mouse on

# ---- 6) 禁止自动重命名窗口（保护你手动起的名字）----
set-option -g allow-rename off
```

```bash

# 或直接命令行让 tmux 重读配置
tmux source-file ~/.tmux.conf
```

### 13. lru_cache（装饰器 / 记忆化）

```python
from functools import lru_cache
fib9 = lru_cache(1)(fib9)   # 把 fib9 包成"带缓存"的版本
```

- `lru_cache(1)(fib9)` 是**包装**不是**调用**：把 fib9 当参数传进去，返回新包装函数，没执行 fib9 的函数体。
- 包装器行为：第一次调用→真正算并缓存结果；之后再调→直接返回缓存，不再算。
- 未缓存时算 fib9，fib0 被调 **21 次**、fib1 被调 **34 次**（指数级重复）；全链 fib0~fib9 都包上缓存后，每个只算 **1 次**，共 10 次。
- **必须全套**（`range(10)` 包 fib0~fib9），只包 fib9 没用，因为 fib9 内部调的 fib8/fib7 没缓存照样重复算。
- `lru_cache(1)` 容量 1 够用，因为这些 fib 无参数、永远返回同一值。
